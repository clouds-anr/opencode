# ANRCode Customization Framework

This document defines the standards for marking, tracking, and governing ANRCode-specific customizations in this fork of [opencode](https://github.com/sst/opencode).

## Why Markers Exist

ANRCode maintains a long-lived fork of the upstream `sst/opencode` project. As the fork diverges, the lack of a standardized marking strategy increases the risk of:

- Merge conflicts during upstream syncs
- Lost customizations
- Duplicate implementations
- Costly upgrade efforts

The `ANRCODE_CHANGE` marker system solves this by making every fork-specific change **visible at a glance** — to developers, AI agents, and automated tooling.

---

## Canonical Marker Format

```
// ANRCODE_CHANGE {"issue":<number>,"branch":"<branch>","date":"YYYY-MM-DD"}
```

### Field Requirements

| Field | Type | Required | Description |
|---|---|---|---|
| `issue` | number | ✅ | GitHub issue number (must be numeric, not a label) |
| `branch` | string | ✅ | The ANR branch this change was made on |
| `date` | string | ✅ | Date of change in `YYYY-MM-DD` format |

### Comment syntax by file type

| File type | Marker syntax |
|---|---|
| TypeScript / JavaScript | `// ANRCODE_CHANGE {...}` |
| Shell scripts (`.sh`) | `# ANRCODE_CHANGE {...}` |
| YAML (`.yml`, `.yaml`) | `# ANRCODE_CHANGE {...}` |
| Config files (`.conf`) | `# ANRCODE_CHANGE {...}` |
| Markdown (`.md`) | `<!-- ANRCODE_CHANGE {...} -->` |
| JSON with comments (`.jsonc`) | `// ANRCODE_CHANGE {...}` |

## Placement Rules

### Newly created file
Place a single marker near the top of the file — after any license header or frontmatter, before the first line of content.

```typescript
// ANRCODE_CHANGE {"issue":350,"branch":"fork-identify-agent-enforce","date":"2026-07-22"}

export function myNewFunction() {
  // ...
}
```

### Modified file
Place the marker **immediately adjacent to the changed region** — directly above the edited block. Do NOT place it at the top of the file unless the top is what changed. This keeps the marker inside the hunk that a merge would conflict on.

```typescript
// existing upstream code above...

// ANRCODE_CHANGE {"issue":350,"branch":"fork-identify-agent-enforce","date":"2026-07-22"}
const command = process.env.CI ? previewCommand : devCommand

// existing upstream code below...
```

### Multiple changes in one file
A file with several unrelated edits may carry several markers — one per changed region. Append rather than replace.

## Exempt Paths

The following paths do **not** require `ANRCODE_CHANGE` markers:

| Path | Reason |
|---|---|
| `packages/anr-core/` | ANR-owned source — entire directory is ANR's |
| `src/generated/` | Auto-generated — do not edit directly |
| `src/generated-effect/` | Auto-generated — do not edit directly |
| `*.lock`, `bun.lockb` | Dependency lockfiles — not source |

## Validating Markers Locally

Before pushing, validate that all your changed files carry markers:

```bash
# Validate specific files
bun run packages/anr-core/script/validate-marker-compliance.ts src/my-file.ts

# Validate all files changed since origin/dev
git diff --name-only origin/dev...HEAD | xargs bun run packages/anr-core/script/validate-marker-compliance.ts

# Detect all fork divergence vs upstream
bun run packages/anr-core/script/detect-fork-divergence.ts
```

## CI Enforcement

Every pull request targeting `dev` runs the **ANRCode Marker Compliance** check (`.github/workflows/marker-compliance.yml`).

Current mode: **warn-only** — the check posts a PR comment listing any missing markers but does not block merging.

Future mode: **hard-fail** — after a grace period, the check will fail the PR if markers are missing.

### Skipping the check

Upstream-sync PRs (auto-generated by the sync workflow) may add `[skip-marker-check]` to the PR title to bypass the compliance check. This override is for upstream-sync PRs only.

## Troubleshooting

### "My file is flagged as missing a marker but it's in packages/anr-core/"
The validator skips `packages/anr-core/` automatically. If you're seeing this, check that your file path starts with exactly `packages/anr-core/`.

### "I have a marker but the validator says it's malformed"
Check that:
- `issue` is a number, not a string (use `350` not `"windows-test-stability"`)
- `date` is in `YYYY-MM-DD` format
- The JSON is valid (no trailing commas, correct quotes)

### "I'm doing an upstream sync — do I need markers?"
No. Add `[skip-marker-check]` to your PR title. The upstream sync workflow does this automatically.

---

## Upstream Sync Guidance

During upstream syncs, `ANRCODE_CHANGE` markers are your primary tool for identifying which hunks are ANR-owned:

1. When a merge conflict occurs, look for `ANRCODE_CHANGE` markers in the conflict region.
2. If the marker is present, the hunk is ANR-owned — preserve the ANR version.
3. If no marker is present, the hunk is upstream-owned — take the upstream version (unless there's a specific reason not to).
4. After resolving, ensure the marker is still present in the resolved file.

The `.github/conflict-rules.conf` file defines path-level ownership rules that complement the marker system.
